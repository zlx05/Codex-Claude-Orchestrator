痛点

单 AI 编程的五个真实问题

一个模型独立完成复杂任务，缺约束、缺审查、缺记录。

01

人工审查疲劳

每次输出都要逐行比对，重复劳动耗光精力。

02

单智能体越改越偏

无人纠正，AI 在错误方向上自我强化。

03

单一模型视角窄

设计盲区无法自检，缺少交叉验证。

04

Token 白白流失

无执行边界，大量 token 耗在无产出探索。

05

决策记录丢失

取舍理由随会话消失，无法追溯复盘。

方案

一个协议，两个角色，工程闭环

Brain Agent 制定计划和控制范围，Hands Agent 在授权边界内执行并生成报告。每个任务都是可追溯的受控回合。

⚡ 协议文件： plan.md · execution.md · review.md
1

创建请求目录

每个任务独立目录，记录目标、语言、轮次、边界。

2

Brain 编写计划

输出 plan.md，指定文件范围、验证命令和验收标准。

3

Hands 执行实现

通过 claude -p 或 codex exec 编码，只触碰授权文件。

4

Brain 审查验收

对照 plan 和 execution 报告，给出 PASS 或 REVISE。

完整流程

从需求到交付，七步闭环

每次任务都是一次受控回合：用户发起，Brain 规划，Hands 执行，Brain 审查，PASS 或 REVISE。

1 User 用户提出需求

在 Codex 或 Claude 对话中用自然语言描述任务目标。如需协作，使用 skill 指令即可自动启用 Brain Agent。

2 Brain 检查仓库并创建请求目录

Brain Agent 检查当前仓库状态、已有文件和项目结构，然后创建独立任务目录。

task/requests/<id>/
3 Brain 编写 plan.md

Brain 生成详细的执行计划：指定允许修改的文件、禁止触碰的范围、验证命令和验收标准。

plan.md
4 Brain 组装 context.md

Brain 将 Executor 协议、plan.md 和配置信息打包为上下文文件，Hands Agent 将以此为执行依据。

context.md
5 Hands 执行实现并写报告

Hands Agent 读取 plan.md 和 context.md，严格在授权范围内编辑文件，运行验证命令，最后写入执行报告。

execution.md
6 Brain 审查执行结果并写审查报告

Brain 读取 execution.md，检查变更文件或 diff，核对 UI 截图等证据，与 plan.md 对照后写出审查结论。

review.md
7 Verdict PASS 交付 或 REVISE 重来

若满足验收标准则 PASS，将最终结果返回给用户。若不满足则 REVISE，Brain 重写 plan.md 进入下一轮，直到到达最大轮次上限。

任务文件

task/ 目录里都有什么？谁读谁写？

每个协作任务在 task/ 下都有完整的文件记录。通过 plan.md、execution.md、review.md 和每轮快照，你可以追溯任何一次改动的决策过程——这不是普通的聊天记录，而是结构化的工程审计轨迹。

📌
task/CURRENT.md
写：Brain 读：Brain / Hands

指向当前活跃请求的指针文件，让两个 Agent 都能定位到正在进行的任务目录。

📝
task/requests/<id>/request.md
写：User 读：Brain / Hands

存储用户原始需求，是整个任务的基础输入。

🧠
task/requests/<id>/plan.md
写：Brain 读：Hands

Brain 的核心输出：指定允许修改的文件、禁止触碰的范围、实现目标和验证命令。

📦
task/requests/<id>/context.md
写：Brain 读：Hands

Brain 将 Executor 协议与 plan.md 打包为完整上下文，Hands 启动时以此为准。

⚡
task/requests/<id>/execution.md
写：Hands 读：Brain

Hands 的执行报告：包含文件变更清单、验证命令输出和问题说明。

🔍
task/requests/<id>/review.md
写：Brain 读：User / 下一轮

Brain 的审查结论：对照 plan.md 核对执行结果，给出 PASS 或 REVISE，下一轮 Brain 也会读取。

📂
task/requests/<id>/history/round-N/
写：Brain（归档） 读：User（审计）

每轮完成后，所有文件（plan、context、execution、review）的不可变快照存档于此。

📸
task/requests/<id>/artifacts/round-N/
写：Hands / Brain 读：Brain / User

存放截图、UI 证据、生成物等验证附件，让审查有据可查。

💡 请求根目录保存最新状态，history/round-N/ 保存每轮审计快照。如果你想了解某个改动是怎么来的，翻看 review.md 和对应轮次的 history 即可——不需要在聊天记录里大海捞针。
回合机制

PASS 还是 REVISE？每轮都有明确结论

任务通过受控回合迭代推进，Brain 决定放行还是修正，直到满足验收标准。

① Plan

Brain 编写 plan.md，定义目标与边界

② Execute

Hands 读取计划，在授权范围内执行

③ Review

Brain 对照计划审查结果，做出裁决

PASS — 所有验收标准已满足，任务完成，结果交付用户。
REVISE — 实现偏离计划或未通过验证，Brain 重写 plan.md 进入下一轮。
最大轮次 — 来自 config.json 的默认上限，防止无限循环。达到上限后强制结束。
快照机制 — 每次迭代的最新文件保存在请求根目录，历史快照存入 history/round-N/，完整审计轨迹永不丢失。
